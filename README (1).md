# AI Chat Assistant

面向超大群的即时需求发现与临时沟通产品。

当用户寻找 ride、超市同行等即时帮助时，系统发现近 3 天的相关消息，让用户围绕具体事项直接聊天，无需加好友，也不继续占用大群消息流。

> 当前阶段：产品定义，尚未实现应用。第一版采用虚构数据和模拟匹配；随后接入真实 AI。此文档中的行为是开发目标，不代表已上线能力。

## 用户问题

- 大群消息更新快，近期需求容易被淹没，相似问题重复出现。
- 一次性协调不一定需要建立好友关系。
- 在大群持续沟通时间、地点等细节会打扰其他成员。

## 核心体验

输入需求 → 私人轻提示 → 查看相关原消息 → 选择需求 → 临时聊天 → 从「正在沟通」继续对话。

例如：输入「周末有人一起去超市吗？」后，看到「近 3 天有 2 条相关需求」，选择 Mia 的 Costco 同行消息，查看上下文，再编辑并发送开场白。

## MVP 范围

| 包含 | 暂不包含 |
| --- | --- |
| 一个虚构学生群，超市同行为主场景 | 对接真实 QQ / 微信 |
| ride、闲聊、过期消息作为匹配测试 | 知识卡片与多人组队 |
| 近期需求提示、列表、原消息详情 | 好友、支付、地图 |
| 一对一事项聊天、正在沟通列表 | 自动替用户发送消息 |
| 本地保存与重置演示 | 第一版真实身份认证与实时通信 |

知识卡片属于后续独立方向：回答「群里已经分享过哪些有用信息」。本轮先验证即时信息卡片的「找人并开聊」价值。

## 推荐触发与屏幕空间

- 浏览群聊时不主动推荐；仅出现「超市」等关键词不足以触发。
- 有明确协调意图并暂停输入约 800ms 后检查。该时长是待测试参数。
- 有结果才显示输入框上方的一行提示；默认不展开完整卡片。
- 提示仅自己可见，不属于群消息；支持关闭，本次草稿不再自动提示。
- 修改需求后旧结果立即失效；较早请求不能覆盖最新结果。
- 忽略推荐可以正常发送原群消息，不拦截、不追加弹窗。
- 自动匹配无结果时保持安静；主动查找无结果时给出明确反馈。
- 中文输入法组合输入期间不触发，完成输入后再计时。

点击提示展开底部面板，收起键盘并保留草稿。结果使用紧凑列表，不使用遮挡信息的堆叠卡片。关闭面板回到原输入状态。实现时需检查焦点管理、移动端键盘和布局跳动。

## 卡片内容与匹配边界

每条结果显示发言者、发送时间、原消息摘要、明确的日期和地点。点击后可查看完整原话及相关回复，再选择「聊聊这件事」。

- 不同人的需求分别展示，不合并成虚构的共同计划。
- 同一需求的改期、取消等后续消息作为上下文处理。
- 近 3 天定义为过去 72 小时；采用明确的当前时间与时区。
- 发布时间在窗口内，不代表事情仍未过期。
- 区分寻找帮助、提供帮助与过去经历；互补需求也可能匹配。
- 未说明的座位、车辆、时间、地点不能推断成事实。
- 未确认是否有效时显示「是否仍在找人待确认」。
- 已明确取消、已满或结束的需求不作为可行动结果默认推荐。
- 原话、头像和身份从数据读取，不由模型编造。

## 事项聊天规则

1. 查看卡片或打开聊天草稿不发送通知。
2. 开场白可编辑，只有用户点击发送后才创建正式会话。
3. 会话顶部保留原需求及共同群来源。
4. 同一对用户针对同一需求再次联系时打开已有会话。
5. 会话内容不回写大群；已开始的对话在「正在沟通」中保留。
6. 演示数据、模拟匹配、模拟对方回复均需清楚标识。
7. 本地存储仅支撑单浏览器 demo，不代表真实多人通信。

## 技术方向

- React + TypeScript，移动端优先。
- 先用固定数据与预设规则跑通交互，再接服务端 AI 匹配接口。
- 第一版 localStorage 保存草稿、会话及会话消息，提供重置入口。
- AI API key 仅存在服务端环境变量中，不写入前端或 Git 仓库。
- 接入 AI 前说明输入草稿的处理方式，并提供关闭自动匹配的选项。
- 真实群聊需单独验证平台消息权限、身份绑定和历史消息覆盖范围。

## 开发与验收

按 [分步开发清单](docs/build-plan.md) 逐项实现。第一阶段完成标准是：输入 → 看推荐 → 查看来源 → 主动发消息 → 返回并继续聊，且刷新后记录仍然存在。

## 待验证的产品假设

- 自动单行提示是否比主动查找更容易发现，又不会干扰输入？
- 原消息与日期信息是否足以帮助用户判断是否值得联系？
- 用户是否理解打开会话不等于已经发送消息？
- 临时会话是否降低了用户发起一次性沟通的顾虑？

通过小规模任务测试记录发现率、完成情况、误解与打断感；不提前宣称效率或转化提升。
